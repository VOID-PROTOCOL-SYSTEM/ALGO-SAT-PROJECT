  1. Your facility is a tree...?
    • As there is only 1 path between any 2 sectors in the network, the Graph ADT doesn't need to check for cycles and so doesn't need to support multiple shortest-path routes. A simple BFS/DFS traversal algorithm will be enough to traverse the network. This further simplifies distance/path computation (BFS terminates with a single unambiguous answer).

In general graphs, there generally exists an alternative route to get around blockages, but trees don't contain this as alt-routes create cycles, and cycles are banned in trees.
  2. Diameter in this network represents the longest shortest path between any two nodes in the facility. It represents that in worst case, if those 2 sectors matter (entry, exit for example), the traversal cost will be greater and so suggests that pure greedy methods may not be optimal here since greedily going for closest supplies may force movement across the diameter multiple times.
  3. A dead end has only 1 way in and out, and backtracking becomes a necessity. It forces a required, unavoidable 'there and back' cost. If supplies weren't in dead ends, they would end up being in through-routes and so wouldn't incur extra costs just to o and collect it. It means that supply collection order becomes very important, a wrong collection order can result in doubling back and forth on the same corridor/s.
  4. Adding corridors turns the tree into a normal graph with cycles, and so, the number of distinct routes between any 2 sectors grows very quickly - 1 extra edge creates a cycle somewhere in the facility. If the facility became fully connected (worst case), possible routes would grow factorially. This suggests that greedy could become more viable since more edges mean shortcuts would exist in the facility and so the penalty for a suboptimal choice would be less significant globally.
  5. An adjacency matrix is an n x n array where n represnts number of nodes in the facility/network. It records whether an edge exists between any 2 nodes and so lookup is O(1), but this method uses n squared memory regardless of the number of edges that actually exist. This makes it more beneficial for dense graphs. Adjacency lists however store edges per node. Edges stored are only the ones that actually connect to it and so uses memory of V + 2E (2E as each edge appears twice, once for each node it connects to) for undirected, or V + E for directed. This makes it much better for sparse graphs. NetworkX uses an adjacency list styled representation, where each graph stores a dictionary of nodes, each connected to a dictionary of its neighbours (and any attribution data). Since Emberlight is a sparse graph (144 nodes & 143 edges), adjacency list is much more efficient to use, needing only 430 cells of data in memory versus 144 squared = 20,736 cells for a matrix - adjacency list is much better.

SIDE MEMO S1-A:

New Operation - unvisited_unclaimed_neighbours(u: Vertex, visited: Set[Vertex], collected: Set[Vertex]) -> Set[Vertex] Behaviour:
  • Precondition: u is a vertex in the graph, visited and collected are the same sets already tracked by the set ADT.
  • Postcondition: returns the subset of neighbours(u) that are neither in visited nor in collecte, and so contains every adjacent reachable sector from u that CRUDY-1 has not already entered, and doesn't contain already recovered supply units.
  • If u is a dead end, and so its only neighbour is already visited, the operation returns an empty set. It's a valid result signalling CRUDY-1 that there is no further movement from u, and so backtracking is required.
  • A neighbour that has a supply unit is included in the result as exclusion only applies to previosuly collected supplies, since uncollected supplies are targets for CRUDY-1.
  • If visited and collected are both empty, then the result is the same as neighbours(u).
Justification: This operation could be written by calling neighbours(u) and then filtering the result through 2 contains() calls (from set ADT). However, every time CRUDY needs to decide where to move next, it must make these 3 calls and if at any time, a filtering call isn't applied or is applied inconsistently, then the routing frontier will be incorrect. Making it a single named operation with a pre-post condition allows every call to get same correct behaviour. This is the same reason neighbours(u), contains() and size() were all formed as first-class operations. It is also an ADT operation as it answers a useful question: 'What is the useful frontier from here?', a question all exploring agents must ask, and this isn't specific to just the Emberlight facility.

RESEARCH AND INQUIRY RESPONSE - PART B

SEARCH ALGORITHMS - GOING DEEPER:

  • Dijkstra's algorithm uses a priority queue based on lowest cost instead of a simple FIFO queue (first-in-first-out) used in BFS. This changes exploration from layer by layer to cheapest cumulative cost first. At each step, the node with lowest known distance from source is checked next, rather than nodes explored in order of discovery. This means that nodes discovered later in searches can be explored before nodes that were discovered earlier due to relative cost. On unweighted graphs, a priority queue acts as a normal FIFO queue since cumulative cost is equivalent to path length.
  • Manhattan distance could be used as a heuristic for this problem since movement is restricted to four directions (up, down, left, right) on a grid, and so diagonal movements are never possible. Since it calculates minimum number of moves needed to reach the goal assuming no walls exist, its heuristic cost will always be equal to or lower than actual cost since the real path has obstacles. This makes the heuristic admissible.
  • Collecting all five supplies before moving to an exit is related to the Travelling Salesman Problem since both involve finding an optimal route to visit a set of fixed locations. This problem is only NP-hard if an optimal path is needed. The problem brief specifies that path length should be minimised. To get a minimal path length, route optimisation is needed and so an exhaustive search based method would need to be implemented causing the problem to be NP-hard. If there is leeway in path length (path doesn't need to be fully optimised), then a greedy solution can be applied removing the NP-hard nature of the problem.

COMPLETENESS & OPTIMALITY:

  • BFS is both complete and optimal on the Emberlight facility since it is guaranteed to find a path (when it exists, as facility is a spanning tree, a path always exists), and since all edges are of equal weight, the first path it finds is guaranteed to be the shortest. The optimisation stage (permutations step) checks varying collection orders and their respective total path lengths, saving the best collection order. This collection order is of lowest cost as it is at every stage compared to the previous best cost, and this route is retained only if better than others. This makes the algorithm both correct and optimal.

REAL-WORLD CONNECTIONS:

  • Real world autonomous systems operating in partially unknown environments generally rely on occupancy grid navigation where grid cells are marked as free, occupied or unknown, and as sensors gather new information, this map is updated. Unlike Emberlight where the entire facility is known in advance, robots may begin with incomplete information and so replan routes as previously unknown cells are revealed, needing use of algorithms capable of efficient replanning (to allow for new shorter/optimal routes to be selected) rather than a single one-off search computed at the start.
  • Monte Carlo Tree Search builds a search tree incrementally by repeatedly simulating random future situations from the current state. It uses the results of the simulations to estimate the most promising movements, and so over time, the most promising branches - reducing search space over time. In Emberlight, the 'game tree' would represent each decision point (junction of corridors) as a choice of directional movement. Random simulations can estimate how many supplies a partial route can get. This allows the search to focus on specific branches over others. However, since Emberlight is fully known from the start and doesn't contain hidden info, this technique isn't needed.
